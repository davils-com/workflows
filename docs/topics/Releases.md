# Releases

<link-summary>Tag-driven releases to pub.dev and GitHub, workspace releases and release-please.</link-summary>

## Tag-driven releases

A tag starts the release of one package:

| Repository | Tag | Pattern (`release.tag-patterns`) |
|---|---|---|
| one package | `v1.2.3` | `single: v{version}` |
| a workspace | `my_core-v1.2.3` | `package: '{package}-v{version}'` |

`release-tag.yml` then runs:

1. **Parse.** The tag matches a pattern, names a package of the repository, carries the version
   of its `pubspec.yaml` (a build number such as `+7` may differ) and is on the release branch
   (`release.verify.on-branch`, `main`).
2. **Verify.** Analyze and test the package, `inspectra check` of the package and the workspace
   root, `pub publish --dry-run`.
3. **Compile and build.** Native binaries of the package's executables, the builds of a Flutter
   app (`build.*`), as release assets.
4. **Publish.** pub.dev with automated publishing (below), after the members the package depends
   on are there.
5. **Release.** The GitHub release: notes, assets, `checksums.txt`, provenance attestations.
   Versions with a pre-release part (`1.0.0-beta.1`) become pre-releases.

A stage only runs when the package has what it needs; `false` turns it off. `release-tag.yml`
with `dry-run: true` runs everything but publishes nothing.

## pub.dev

pub.dev accepts the OpenID Connect token of the publish job, so no credential is stored. Set up
each package once on pub.dev, Admin, Automated publishing:

- Repository: `davils-com/<repository>`
- Tag pattern: `v{{version}}`, or `<package>-v{{version}}` in a workspace
- Require GitHub Actions environment: `pub.dev` (recommended), and create that environment in the
  repository; a deployment rule limited to tags keeps branches from publishing

pub.dev only accepts runs that the push of a matching tag started. The token carries the caller's
repository, event and ref, so the publication works although the workflow lives in
davils-com/workflows. A rerun of a release whose version is on pub.dev already succeeds without
publishing (`skip-existing`).

## Workspace releases

Push the tags of all members to release together. Each release waits on pub.dev for the lowest
version of every member it depends on (`release.pub.wait-for-siblings`, 60 attempts, 30 seconds
apart), so the members publish in the order of their dependencies.

**GitHub starts no workflow when more than three tags arrive in one push.** Push them three at a
time:

```bash
tools/push-tags.sh            # every local tag the remote does not have
tools/push-tags.sh a-v1.0.0 b-v1.0.0 c-v1.0.0 d-v1.0.0
```

`release.github.make-latest: auto` marks a package release as the latest release; with
`latest-package` only that package's releases do.

## Release notes

`release.github.notes-source`:

| Value | Notes |
|---|---|
| `auto` | Inspectra when the package has an Inspectra configuration, else the version's section of `CHANGELOG.md`, else generated by GitHub; an existing release keeps its notes |
| `inspectra` | `inspectra changelog notes <version>`; the release stops when there are none |
| `changelog` | the section `## [1.2.3]` or `## 1.2.3` of the package's `CHANGELOG.md` |
| `file` | a file of the repository |
| `generate` | GitHub's notes from the merged pull requests |
| `keep` | the body of the existing release, such as release-please's |

## release-please

`release.mode: release-please` (auto when `release-please-config.json` exists) runs
release-please on pushes to the release branch. It keeps a release pull request with the next
versions and changelogs from Conventional Commits; merging it creates the tags and releases.

The tags have to start the tag-driven release, because pub.dev only accepts tag pushes. Tags
created with the workflow's `GITHUB_TOKEN` start no workflow, so:

| `release.release-please.token-source` | How the release starts |
|---|---|
| `app` (default) | A GitHub App's token (secrets `RELEASE_APP_ID`, `RELEASE_APP_PRIVATE_KEY`) creates the tags; their push starts the caller's workflow, which runs the tag-driven release and completes the GitHub release with assets |
| `pat` | The same with a personal access token in `RELEASE_PLEASE_TOKEN` |
| `github-token` | `release.release-please.dispatch-workflow` names the caller's workflow; it is started with `workflow_dispatch` on each new tag. pub.dev has to allow publishing from `workflow_dispatch` events. |

For a workspace, `release-type: dart` per package with `include-component-in-tag: true` and
`tag-separator: "-"` gives `<package>-v<version>` tags; `linked-versions` keeps members in step.
See `examples/release-please`. `release.release-please.back-merge` opens a pull request from the
release branch back into the integration branch after each release.
